# Four-Module Modular Architecture

**Decision (October 2025, Pivot 1 — researchplan.tex §1.3): Abandon the single monolithic fine-tuned model in favour of four loosely-coupled, separately-diagnosable components communicating through well-defined interfaces. This decision is binding and is the structural frame for every implementation choice in the thesis.**

## Why

Professor Conlan identified the core failure of the original plan (fine-tuning LLaMA-7B or Mistral-7B with multi-task objectives): catastrophic forgetting operates at every level simultaneously. Improving mathematical reasoning degrades empathetic generation because both tasks require different activation patterns in the shared layers. Fine-tuning on one user's preferences overwrites knowledge from prior users, making true personalisation impossible. When the system fails, the failure cannot be attributed to a specific capability because all capabilities share the same weight space. Feedback received: "if the system gives a wrong answer, is that a reasoning failure, a User Modelling failure, or a generation failure? Impossible to diagnose."

**Why:** Monolithic fine-tuning cannot simultaneously be empathetic, logically rigorous, and personalised without catastrophic forgetting. Modularity is the architectural prerequisite for trustworthiness, scrutability, and independent evaluation.

**How to apply:** Every implementation decision must be mapped to exactly one module. If a proposed change would require two modules to share state through weights rather than well-defined interfaces, it is a red flag — propose a structural alternative.

## The Four Modules

| Module | Responsibility | Implementation | Trainable? |
|---|---|---|---|
| **Reasoning Module** | Problem decomposition, logical inference, constitutional trustworthiness | Qwen3-0.6B (primary) / Gemma 4 (secondary), fine-tuned via SFT + GRPO with composite constitutional reward | Yes — SFT + GRPO |
| **User Modelling Module** | Persistent 5W+H user profiles: goals, skills, context, preferences, interaction history | Structured knowledge graph (FalkorDB + Cognee) on local MCP server; no weights, no training | No — structured DB |
| **Tool Integration Layer** | Delegation decisions, MCP tool invocation, output logging for explainability | Orchestration logic; every invocation logged with inputs, outputs, and reasoning that led to delegation | No — rule-based |
| **Generator Module** | Final response synthesis: combines reasoning output + user context + tool results into NL | Base LLM (prompting + RAG); may share weights with Reasoning Module; no additional fine-tuning on user data | No — prompting only |

## Key architectural properties

The User Modelling Module is explicitly NOT a neural network — it is a structured database. This means there is no fine-tuning on user data, no catastrophic forgetting of previous users, no mixing of one user's psychological profile with another's, and no weight update that could silently degrade constitutional behaviour. The 5W+H schema gives it explicit, inspectable slots rather than latent embeddings. This is what makes personalisation scrutable: the user can read a graph node, not a weight matrix.

The Tool Integration Layer is orchestration logic, not learned behaviour. Every delegation decision is logged with the reasoning that produced it. This is the thesis's explainability mechanism — not post-hoc rationalisation generated by asking "why did you do that?", but actual logs of the decision-making process as it happened.

The Generator Module does not need fine-tuning because it combines reasoning traces, retrieved user context, and tool outputs through structured prompting. Adding fine-tuning to the Generator would reintroduce catastrophic forgetting risks.

## Local-first privacy by architecture

The User Modelling Module runs entirely on the user's own device via local MCP servers. No user-specific data is transmitted to a remote server. The core security argument: a model that physically cannot exfiltrate data does not need to be trusted not to. This is an unconditional guarantee, stronger than any privacy policy.

## What this is NOT

- Not a model with multiple output heads sharing one weight space.
- Not a model that learns user preferences through weight updates.
- Not a system where empathy, reasoning, and personalisation share the same layers.
- Not a cloud-hosted personalisation system.

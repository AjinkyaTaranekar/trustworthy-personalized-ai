# T1: A Tool-Oriented Conversational Dataset for Multi-Turn Agentic Planning

**A synthetically-generated, human-verified multi-turn dataset (13.5k dialogues, 9 domains, 14 tools) purpose-built to stress-test whether tool-using agents can plan across inter-tool dependencies — where one tool's output feeds another's arguments — shipping an evaluation harness with a caching (memory) mechanism and execution-grounded metrics; SFT on it lifts an 8B model past a 70B base on tool selection.**

## Summary

Chakraborty et al. (Capital One Research, 2025) target inter-tool dependency planning in multi-turn dialogue — the case most tool-use benchmarks under-test. T1 deliberately builds tasks where an agent must call a tool, cache the result (`save_to_cache`/`get_results_from_cache`), reuse or filter it later, and replan when the user changes constraints. Its five-facet harness (T1-Agent) verifies tool selection, parameter matching, sandbox code-execution rate, information-seeking, and cache summaries. The headline: SFT on the T1 split lifts Llama-3.1-8B Tool Call F1 52.11 → 87.17 and Param-Match F1 31.79 → 75.76, **beating the 70B base (79.72)**. This is direct evidence that tool-use competence transfers via targeted SFT rather than requiring scale — the premise behind a small executor.

## Why it matters here

The single most citable number is 8B-SFT > 70B on tool selection — support for the small-executor half of a thinker-executor design. The template → annotate → lexicalize pipeline is a reproducible recipe for generating multi-turn tool-call training data with verifiable ground truth (what the [[experiments/thinker-executor-experiment|Executor]] needs), and the five-facet harness — especially sandbox **code-execution rate** — is a template for verifying an on-device executor's calls beyond string match. The cache tools are a lightweight tool-mediated memory relevant to on-device agents that cannot hold huge context.

## Method

- **Three-step construction:** template generation (Llama-3.3-70B) → human QA (five annotators) → programmatic lexicalization from a large synthetic ontology (480k flights, 47k hotels, …).
- **9 domains** (4 single + 5 multi), 13.5k dialogues, 6.0–11.3 avg turns.
- **14 tools** in three classes, including memory tools `save_to_cache`, `get_results_from_cache`, `filter_flights`.
- **T1-Agent metrics:** Tool Call F1, Parameter Matching, sandbox Code-Execution Rate, Information Seeking (SacreBLEU/BERTScore), Cache Summary (exact match).

## Key results

- **Llama-3.1-8B SFT:** Tool Call F1 52.11 → **87.17**, Param-Match F1 31.79 → **75.76**, exceeding Llama-3.3-70B (79.72 / 67.74) — though 70B still leads raw code-exec (91.43% vs 84.29%).
- Frontier tops out ~91–94 F1 (Gemini 2.5 Pro 94.28, GPT-5 93.14).
- Few-shot gains plateau beyond 5 shots; reasoning models (s1.1-32B, Phi-4-reasoning) show reasoning ≠ good tool selection.

## Critical appraisal

Honestly-scoped; the real value is the inter-tool-dependency + caching framing that most benchmarks miss, and the clean "8B-SFT beats 70B" small-model story. Caveats: entirely *synthetic and travel-domain* (real APIs are messier); template-derived ground truth means exact-match metrics may under-credit valid alternative tool orders; the SFT gain is in-distribution (shared 9 domains / 14 tools), so it is a domain-adaptation result.

> ⚠ 0.6B caution: the smallest model is 8B; the 52→87 SFT jump is untested at 0.6B, and reasoning-heavy models show reasoning tokens alone don't produce runnable tool calls without executor-side SFT.
